1. Executive Summary

1.1 Project Goal

Add VulkanVideoEncodeAccelerator as a peer of VaapiVideoEncodeAccelerator, V4L2VideoEncodeAccelerator, D3D12VideoEncodeAccelerator and MediaFoundationVideoEncodeAccelerator so Chromium can use VK_KHR_video_encode_queue for:

  • Cross-platform HW encode (Linux, Android, Windows, Stadia-like cloud) behind a single backend.
  • Vendor-agnostic encode that ships in the same Vulkan ICD used by the rasterizer/compositor — no separate VA-API / MFT drivers needed.
  • Direct integration with Chromium's Vulkan compositor (SkiaRenderer) — input frames stay as VkImage end-to-end.
  • A unified backend for decode + encode (transcoding, WebRTC loopback, screen capture).

1.2 Interface boundary — Chromium-side surface is codec-neutral

Where does codec-specific code live? This is the question that drives the integration shape. There are three reasonable layers and only the middle one moves between options:
LayerCodec-aware?Who writes it?
A. Chromium VEA / WebRTC / WebCodecs (Mojo-stable)No — generic VideoEncodeAcceleratorChromium (already exists)
B. Codec driver loop: parameter sets, DPB slots, slice headers, vkCmdEncodeVideoKHR with VkVideoEncodeH264PictureInfoKHR / StdVideoEncodeH264*Yes — heavilyEither Chromium (from-scratch plan) or the upstream library (recommended Model D)
C. Vulkan driver / VK_KHR_video_encode_h264Yes (this is the codec spec)NVIDIA / AMD / Intel ICD

The recommended Model D / Model A moves Layer B inside the upstream Vulkan-Video-Samples library. The Chromium-side surface that talks to the library is: 

// Per-session (set once at Initialize):
VkVideoEncoderConfig {
    codec  = VK_VIDEO_CODEC_OPERATION_ENCODE_H264_BIT_KHR;   // ← codec set here, once
    encodeWidth/Height, inputFormat, bitDepth,
    rateControlMode, GOP, color/VUI params,
    externalDevice, externalInstance, ...
};

// Per-frame (codec-neutral):
SubmitExternalFrame(VkVideoEncodeInputFrame {
    VkImage image, ...,
    VkBool32 forceIDR, int32_t qpOverride,
    wait/signal semaphores,
});
GetEncodedFrame(VkVideoEncodeResult {
    const uint8_t* pBitstreamData, uint32_t bitstreamSize,
    uint32_t pictureType (0=I, 1=P, 2=B), VkBool32 isIDR,
});

No VkVideoEncodeH264PictureInfoKHR, no StdVideoEncodeH264SliceHeader, no per-codec union ever appears on the Chromium ↔ library surface. That is exactly the codec-neutral "frame-in / bitstream-out" model.

Sections §1.2 through §5 below were written for the original from-scratch plan (where Chromium would have written Layer B itself, with per-codec H264VulkanVideoEncoderDelegate / H265… / AV1… classes). They are preserved as a reference for how the codec driver loop works internally — useful for review, for fallback Model B (vendor codec layer), and for understanding what the library does on our behalf. For the recommended Model D / Model A path, all of §1.2 §4 §5 collapses into "configure VkVideoEncoderConfig.codec; the library does the rest." See VULKAN_VIDEO_LIBRARY_INTEGRATION_ANALYSIS.md for the recommended path.

1.2.1 Key Insight (from-scratch plan): GOP / DPB / Rate Control are NOT Shared

Applies to: from-scratch plan and Model B fallback. The whole "DPB / GOP / rate control is per-backend" framing below describes work the library has already done internally for Model D / A — Chromium just sets the parameters in VkVideoEncoderConfig once.

Decoding in Chromium reuses parsers (H264Parser, H265Parser, ...) across backends. Encoding is the opposite:

ComponentDecode (existing)Encode (this design)
Bitstream parsingShared in media/parsers/N/A — encoder emits
DPB / reference frame logicShared in H264Decoder, H265Decoder ...Per-backend
GOP / rate controlDecoder consumesPer-backend (re-implemented)
Bitstream builderH264SliceHeader → parserShared in media/filters/h26x_annex_b_bitstream_builder.h
HW driver callvkCmdDecodeVideoKHRvkCmdEncodeVideoKHR

What Chromium already gives us for encode:

  • media/video/video_encode_accelerator.h — the stable IPC-facing VideoEncodeAccelerator (VEA) interface: the C++ contract every HW encoder backend (VaapiVideoEncodeAccelerator, D3D12VideoEncodeAccelerator, MediaFoundationVideoEncodeAccelerator, the proposed VulkanVideoEncodeAccelerator) implements. It is Mojo-stable, so the renderer process talks to whichever backend the GPU process selected without knowing which one it is.
  • media/gpu/h264_dpb.{h,cc}, media/gpu/h264_ratectrl_rtc.{h,cc} — DPB and SW rate controller (reusable).
  • media/gpu/h264_builder.{h,cc}, media/filters/h26x_annex_b_bitstream_builder.h — Annex-B header builders (reusable).
  • media/gpu/svc_layers.{h,cc} — SVC scalability layer math.

What we must write:

  • NEWVulkanVideoEncodeAccelerator
  • NEWVulkanVideoEncoderWrapper
  • NEWVulkanVideoEncoderDelegate + per-codec subclasses (H.264, H.265, AV1)
  • NEWConversion: H264SPS/PPS/SliceHeader → StdVideo* structures
  • NEWDPB slot manager bound to VkVideoReferenceSlotInfoKHR[]
  • NEWBitstream readback via VK_QUERY_TYPE_VIDEO_ENCODE_FEEDBACK_KHR

VA-API does not support HEVC encode in tree. There is no h265_vaapi_video_encoder_delegate.{h,cc}; the VA-API VEA unit test documents this explicitly. Our HEVC delegate ports its Chromium-side state machine from media/gpu/windows/d3d12_video_encode_h265_delegate.{h,cc}, and its Vulkan command flow from VkVideoEncoderH265.cpp.

Same Std-video structure pattern as H.264. HEVC adds a StdVideoH265VideoParameterSet via VkVideoEncodeH265SessionParametersAddInfoKHR and prepends VPS+SPS+PPS bytes on IDR (we prefer the bytes returned by vkGetEncodedVideoSessionParametersKHR() when the driver advertises overrides).

5.4 AV1

Driver emits all OBUs (sequence header, frame header, tile group) — we never splice in "packed headers" and set precedingExternallyEncodedBytes = 0 on every frame.

6. Input Path: VideoFrame → VkImage

Review F7: the negotiated input mode (Config::StorageType::kShmem vs kGpuMemoryBuffer) is not the same as the frame-time VideoFrame::storage_type() (commonly STORAGE_MAPPABLE_SHARED_IMAGE in current GPU-backed paths). The diagram below labels columns by negotiated mode and names the platform realisations underneath.
A. shmem (stage + copy). B. kGpuMemoryBuffer via the proposed SharedImageManager::ProduceVulkanVideo() → new VulkanVideoImageRepresentation → scoped read access. C. Platform fallbacks (DMA-BUF / Win NT handle / AHardwareBuffer) when the shared-image path declines. Same pattern as D3D12VideoEncodeAccelerator's existing SharedImageManager::ProduceVideo() flow.
Review F6: we do not reach into the shared image directly. We go through CommandBufferHelper::GetSharedImageManager() → the proposed ProduceVulkanVideo() → BeginScopedReadAccess(), modeled after the D3D12 path that already exists in ToT for D3D11 textures. This keeps lifetime, synchronisation, and forward compatibility correct.
The seam as implemented on vulkan-on-chrome/dev: ProduceVulkanVideo() succeeds iff the producer pool tagged the SharedImage with SHARED_IMAGE_USAGE_VIDEO_ENCODE_ACCELERATOR; untagged frames fall back to the shmem staging ladder. Tagging is per producer pool (P0 adapter — done; P1 RTCVideoEncoder; P2 viz capture pool). Producer matrix and plug-in order: use-cases document.

7. Rate Control, GOP, Quality Level and QP Maps

Three rate-control modes; each mode applied via vkCmdControlVideoCodingKHR(VK_VIDEO_CODING_CONTROL_ENCODE_RATE_CONTROL_BIT_KHR).

7.1 VUID rules — ValidateRateControl() (Review F4)

Vulkan attaches non-obvious validity rules to VkVideoEncodeRateControlInfoKHR. We centralise them in VulkanVideoEncoderWrapper::ValidateRateControl(); per-codec delegates never set the fields directly.
ModelayerCountPer-layer constraint
DEFAULTmust be 0n/a (driver decides everything)
DISABLEDmust be 0n/a (per-frame QP via codec-specific constantQp, see §7.2)
CBR≥ 1 (== temporal-layer count)each: averageBitrate == maxBitrate
VBR≥ 1 (== temporal-layer count)each: averageBitrate ≤ maxBitrate ≤ caps.maxBitrate

7.2 Software Rate Controller + per-codec constantQp (Review F5)

For external / CQP mode the QP needs to be communicated through two Vulkan fields, not just slice_qp_delta:

  1. rateControlMode = VK_VIDEO_ENCODE_RATE_CONTROL_MODE_DISABLED_BIT_KHR with layerCount = 0.
  2. The per-slice / per-frame constant-QP field the driver actually reads in disabled-RC mode:
    • H.264: VkVideoEncodeH264NaluSliceInfoKHR::constantQp
    • H.265: VkVideoEncodeH265NaluSliceSegmentInfoKHR::constantQp
    • AV1: VkVideoEncodeAV1PictureInfoKHR::constantQIndex
  3. slice_qp_delta on the matching StdVideo*SliceHeader so the emitted slice header decodes to the same QP.
  4. Clamp to [caps.minQp, caps.maxQp] and the profile range.

7.3 Quality Level

VK_KHR_video_encode_queue revision 9 added VkVideoEncodeQualityLevelInfoKHR, an integer 0..(maxQualityLevel-1). We map Chromium's ContentType:

ContentType::kCamera (low-latency RTC)maxQualityLevel - 1 (fastest)
ContentType::kDisplay (screen content)maxQualityLevel / 2 (balanced)

7.4 Quantization Maps and Intra-refresh

Phase-6 extensions. VK_KHR_video_encode_quantization_map binds EncodeOptions::quantizer; VK_KHR_video_encode_intra_refresh maps WebRTC's kRealtimeVideo retransmit recovery.

7.5 Manual reference buffer control (Review F9)

MVP declines: if Config::manual_reference_buffer_control == true we return EncoderStatus::Codes::kEncoderUnsupportedConfig and publish VideoEncoderInfo::number_of_manual_reference_buffers = 0. Phase-6 will map EncodeOptions::reference_buffers[] → VkVideoEncodeInfoKHR::pReferenceSlots and update_buffer → pSetupReferenceSlot->slotIndex.

8. Bitstream Output, Queries and Feedback

Bitstream readback path with VK_QUERY_TYPE_VIDEO_ENCODE_FEEDBACK_KHR and Annex-B composition.

8.1 dstBufferOffset + precedingExternallyEncodedBytes (Review F2)

What v1.0 got wrong: v1.0 said headers are prepended after readback. That is fine for the bytestream but it lies to the driver's rate controller — the driver doesn't know about header bytes when choosing QP for the IDR.

v1.1 reserves header space before the encode call and tells the driver:

const uint32_t header_size = pic->idr ? PrepareHeaderBytes() : 0;
encode_info.dstBufferOffset                  = header_size;
encode_info.dstBufferRange                   = bitstream_size_ - header_size;
encode_info.precedingExternallyEncodedBytes  = header_size;
// Final shmem:
//   shmem[0 .. header_size)        = app-built / driver-fetched SPS/PPS/VPS/AUD
//   shmem[header_size .. +N)       = slice bytes written by the driver

For frames where the driver advertises VK_VIDEO_ENCODE_FEEDBACK_BITSTREAM_HAS_OVERRIDES_BIT_KHR or the session was created with VK_VIDEO_SESSION_CREATE_ALLOW_ENCODE_PARAMETER_OPTIMIZATIONS_BIT_KHR, we prefer the bytes returned by vkGetEncodedVideoSessionParametersKHR() over our own H26xAnnexBBitstreamBuilder. For AV1 the driver writes the entire stream, so header_size = 0.

8.2 Inline query vs Begin/End query (Review F3)

Both paths must remain in tree (some shipping drivers lack VK_KHR_video_maintenance1):

if (video_maintenance1_supported_) {
    // Inline query - chain into VkVideoEncodeInfoKHR
    VkVideoInlineQueryInfoKHR inline_query = { ... };
    ChainNext(encode_info, inline_query);
    vkCmdEncodeVideoKHR(cmd_buf, &encode_info);
} else {
    // Begin/End-query fallback (matches Vulkan Samples)
    vkCmdBeginQuery(cmd_buf, encode_feedback_query_pool_, query_slot, 0);
    vkCmdEncodeVideoKHR(cmd_buf, &encode_info);
    vkCmdEndQuery(cmd_buf, encode_feedback_query_pool_, query_slot);
}

8.3 Result statuses (and the careful re-encode rule)

StatusAction
COMPLETE_KHRRead offset/size, copy to shmem, deliver
NOT_READY_KHRWait again
ERROR_KHRReport kEncoderFailedEncode
INSUFFICIENT_BITSTREAM_BUFFER_RANGE_KHRReplay-safe only. If no later frame has been issued, grow the buffer and re-encode. If we already pipelined past this frame, fail this frame and force a keyframe on the next; grow the buffer ceiling for subsequent encodes.

9. Synchronization, DMA-BUF and Cross-Queue Handoffs

Three queues from the same VkDevice; coordinated via a single timeline semaphore. sync2 is mandatory for encode.
  • Graphics queue — compositor, input pre-processing.
  • Transfer queue — DMA-BUF imports, staging copies.
  • Video encode queue — vkCmdEncodeVideoKHR.

DMA-BUF sync FDs are imported via VK_KHR_external_semaphore_fd so we avoid relying on kernel implicit-sync (which can stall the entire pipeline).

10. Protected (DRM) Content for Encode — Non-goal (Review F12)

Protected encode is explicitly not in scope for this design's MVP and is not in the execution plan. The block below exists so future work can pick it up cleanly when a real consumer materialises.

Why it's a non-goal: WebRTC, MediaRecorder, WebCodecs, screen capture, tab capture — all consume clear content and produce clear bitstream. Widevine's CDM API only exposes decryption keys. HDCP re-encryption for simulcast is not a feature Chrome currently asks for. Implementing protected encode requires a protected VideoFrame source, a Chrome/CDM contract for encryption keys, a protected destination VkBuffer, a protected-aware Mojo path, and a protected client — none of which exists today.

If a caller requests it, we return EncoderStatus::Codes::kEncoderUnsupportedConfig.

Trigger to revisit: a Chrome product asks for it, CDM exposes encryption keys, and at least one Vulkan ICD advertises protected encode capabilities on a platform Chrome targets.
