1. Overview — one funnel, six consumers

Every hardware-encode consumer in Chromium — WebRTC calls, screen sharing, WebCodecs, MediaRecorder, Cast mirroring, Chrome Remote Desktop — discovers encoders through a single GPU-process funnel: GpuVideoEncodeAcceleratorFactory::CreateVEA(). On the vulkan-on-chrome/dev branch, VulkanVideoEncodeAccelerator registers first in that factory's list behind the VulkanVideoEncode feature, so all six use cases pick it up automatically — no per-consumer wiring is needed for functionality. What does need per-consumer work is zero-copy, because the decision "can this frame be encoded without a CPU copy?" is made where the frame's SharedImage is created, not where it is consumed (§3).

All browser encode use cases funnel into the GPU-process factory; the Vulkan backend and vendored NVPRO library sit below it, on the compositor's own VkDevice.
Why this matters strategically on Linux/NVIDIA Upstream Linux HW encode is default-off (kAcceleratedVideoEncodeLinux, media/base/media_switches.cc:704) and VA-API is additionally disabled on NVIDIA GPUs (kVaapiOnNvidiaGPUs, :716, crbug.com/1492880). Stock Chrome on an NVIDIA Linux desktop therefore has no hardware encode path at all — every Meet/Zoom/Discord call burns CPU on libvpx/OpenH264. The Vulkan backend is the first real HW encode path for this platform.

2. The use cases in detail

U1 — WebRTC camera call encodes via fallback · zero-copy after P1 · ship needs G-NEW-3/6

Entry chaingetUserMedia → RTCPeerConnection → webrtc VideoStreamEncoder → blink::RTCVideoEncoderFactory → blink::RTCVideoEncoder(::Impl) → MojoVideoEncodeAccelerator (third_party/blink/renderer/platform/peerconnection/rtc_video_encoder.cc). Does not use VideoEncodeAcceleratorAdapter — it has its own frame preparation.
Encoder discoveryRTCVideoEncoderFactory::GetSupportedFormatsInternal() maps GetVideoEncodeAcceleratorSupportedProfiles() → SDP formats; codec gates: kWebRtcAV1HWEncode (AV1), kPlatformHEVCEncoderSupport + kWebRtcAllowH265Send (H.265). Advertised scalability_modes come from the VEA profile — a HW encoder is only picked for L1T2/L1T3 if it reports them.
Frame source & storageLinux V4L2 camera → CPU I420 buffers. Impl negotiates "NV12 + kGpuMemoryBuffer" or "I420 + kShmem" (:1112). CPU frames are converted+copied into RTCVideoEncoder's own NV12 SharedImage (CreateNV12SharedImageFrame, :2166) whose usage is CPU_WRITE_ONLY | DISPLAY_READ (:682) — no encode tag → staging fallback today.
Encoder demandsCBR with dynamic bitrate (congestion control calls RequestEncodingParametersChange continuously — currently a documented no-op, needs library G-NEW-3); temporal layers L1T2/L1T3 for adaptation (G-NEW-6; today layerCount==1); simulcast via Config::SpatialLayer (kRtcVideoEncoderConvertSimulcastToSvc rewrites simulcast→SVC); frame-drop feature kWebRTCHardwareVideoEncoderFrameDrop; keyframe-on-demand (works — G-6 forceIDR).
Observabilitychrome://webrtc-internals outbound-rtp: encoderImplementation shows the VEA class name (ours: "VulkanVideoEncodeAccelerator"), plus powerEfficientEncoder, qualityLimitationReason, totalEncodeTime, qpSum. Both impl fields require the page to be actively capturing.
Status on devReachable and encodes correctly through the staging fallback (2 CPU copies/frame). Zero-copy = P1 one-line tag. Shipping quality = library G-NEW-3 + G-NEW-6.

U2 — Screen share (getDisplayMedia → WebRTC) same client as U1 · GPU-native source · zero-copy after P2

Entry chainIdentical send path to U1 (there is no separate encoder for screen share). What differs is the source: viz::FrameSinkVideoCapturerImpl (components/viz/service/frame_sinks/video_capture/) captures compositor output via CopyOutputRequest.
Frame source & storageThe capturer's GpuMemoryBufferVideoFramePool delegates to media::RenderableGpuMemoryBufferVideoFramePool, which creates GPU-native NV12 SharedImages with usage GLES2_R/W | RASTER_R/W | DISPLAY_READ [| SCANOUT] (renderable_gpu_memory_buffer_video_frame_pool.cc:224) — no encode tag. The pixels are born in the GPU process, cross to the renderer as a mailbox only, and come back to the GPU process for encode — where they currently take a pointless CPU round-trip.
Encoder demandsAs U1, plus screen-content specifics: ContentType::kDisplay (from contentHint / capture type), very low fps with sudden bursts, high-detail intra, intra-refresh for recovery (G-NEW-5, deferred).
Status on devEncodes via fallback. P2 (tagging the renderable pool, opt-in) turns this into the flagship all-GPU graph: compositor → capturer → encoder with zero CPU bytes — the DDD Phase-4 exit criterion. Watch SCANOUT+encode modifier compatibility on NVIDIA.

U3 — WebCodecs VideoEncoder works today on dev (P0) — CPU sources zero-copy

Entry chainblink::VideoEncoder (modules/webcodecs/video_encoder.cc) → CreateAcceleratedVideoEncoder() (:648) → media::VideoEncodeAcceleratorAdapter wrapped in VideoEncoderFallback (SW fallback to libvpx/libaom/OpenH264 unless prefer-software). No "broker" exists on the encode side (decode has one; encode does not).
Config mappinghardwareAcceleration → EncoderType (no-preference still tries HW first); latencyMode → realtime vs quality; contentHint → camera vs display content type; bitrateMode: quantizer → Bitrate::Mode::kExternal → per-frame QP (encodeOptions.avc.quantizer) → Vulkan rateControlMode=DISABLED. isConfigSupported({hardwareAcceleration:'prefer-hardware'}) is the JS-level probe — resolves supported:false on stock Linux (renderer gate off).
Frame source & storageCPU frames (camera track, ImageBitmap): copied once into the adapter's mappable-SI pool — which dev tags with VIDEO_ENCODE_ACCELERATOR (adapter.cc:217) → zero-copy from there. GPU frames (canvas/WebGL/<video>): passed through unchanged (:1088) with their producer's untagged usage → staging fallback (P3 decision pending).
Encoder demandsBoth CQ (per-frame QP) and CBR/VBR; flush() drain; L1T1–L1T3 via scalabilityMode (needs G-NEW-6); optional QP maps later (G-NEW-4 / VK_KHR_video_encode_quantization_map).
Status on devThe proven path: this is what the zero-copy gate script drives; measured zero-copy=58/staging=2 on a 60-frame run, bit-identical output vs staging, 51.07 dB PSNR at CQP=26 on the A4000.

U4 — MediaRecorder works today on dev (P0) — shares the adapter path

Entry chainMediaRecorder → media_recorder_handler.cc → VideoTrackRecorderImpl → HW callback builds media::VideoEncodeAcceleratorAdapter (video_track_recorder.cc:316) with EncoderType::kHardware; SW fallback on OnHardwareEncoderError. Selection consults kPreferredCodecAndVEAProfiles and min-resolution gates (kVEAEncoderMinResolutionWidth/Height).
Frame sourceAny MediaStreamTrack: camera (CPU), tab capture (GPU — U2's source), canvas capture. Same adapter dichotomy as U3.
Encoder demandsVBR rate control (the one consumer that defaults to VBR); Flush() drain-once semantics on stop; long-session stability (hours); muxable output (Annex-B → MP4/WebM muxers in Blink). H.265 recording is HW-only and default-on since M136 — a future HEVC target.
Status on devWorks via the tagged adapter pool exactly like U3. Essentially untested end-to-end in the TEST_PLAN (its only mention is a rate-control matrix row) — recipe §6.4 closes that gap cheaply.

U5 — Cast mirroring / tab cast undocumented in DDD/TEST_PLAN · works via factory · zero-copy after P2

Entry chaincomponents/mirroring/service/openscreen_session_host.cc (CreateVideoEncodeAccelerator() wraps MojoVideoEncodeAccelerator directly) → media/cast/encoding/video_encoder.cc::Create() → if use_hardware_encoder: SizeAdaptableExternalVideoEncoder → ExternalVideoEncoder(VEAClientImpl) (media/cast/encoding/external_video_encoder.cc). Capability gating in encoding_support.cc.
Frame sourceviz FrameSinkVideoCapturerImpl — the same capture stage as U2, so P2 unlocks both.
Encoder demandsReal-time CBR at fixed latency budget; keyframe-on-demand for receiver recovery; HW-first is default: CastStreamingOfferHardwareFirst enabled, per-codec pins --cast-streaming-force-{enable,disable}-hardware-{av1,h264,hevc,vp8,vp9}; frame-drop feature kCastVideoEncoderFrameDrop.
StatusReachable through the factory like everyone else, but absent from the DDD and TEST_PLAN (known documentation gap). Since Cast is HW-first by default, it may be the first surface users hit organically once the feature ships — add it to the TEST_PLAN when P2 lands (shares U2's graph up to the client).

U6 — Chrome Remote Desktop niche · Windows-oriented · inherits backend for free

Entry chainremoting/codec/webrtc_video_encoder_gpu.cc calls GpuVideoEncodeAcceleratorFactory::CreateVEA/GetSupportedProfiles directly (in-process, COM-init under IS_WIN). The web client mostly decodes.
StatusNo work planned; listed for completeness — it inherits whatever the factory offers.

3. The common trunk and the zero-copy seam

Below the Mojo boundary all use cases share one trunk: MojoVideoEncodeAcceleratorService → factory → VulkanVideoEncodeAccelerator, which dispatches per frame on frame->HasDirectCpuAccess(): CPU frames take the §6.1 staging path (LINEAR NV12 VkImage, libyuv write, library does the LINEAR→OPTIMAL copy on the encode queue); SharedImage frames take the §6.3.2 zero-copy resolve (SharedImageManager::ProduceVulkanVideo → VkImage with VIDEO_ENCODE_SRC usage + acquire/release semaphores + FOREIGN→encode queue-family transfer).

The single load-bearing predicate OzoneImageBacking::ProduceVulkanVideo succeeds iff the SharedImage was created with SHARED_IMAGE_USAGE_VIDEO_ENCODE_ACCELERATOR — a new usage bit (1u<<28) introduced on dev (ozone_image_backing.cc:547). That bit is set at producer pool creation time, in renderer/viz code the encoder never sees. "Plugging in zero-copy" for a use case therefore means one thing: tag its producer pool. The GPU-side machinery (backing-factory acceptance, dma-buf import rules, sync, fallback ladder) is already complete.
Producer pools on the left decide the outcome; the GPU-process resolve, fallback ladder and Wayland import rules are shared by all use cases.

5.1 The GPU-RGB input path (P3-RGBA) — where libyuv actually sits, and how to avoid it

The all-GPU RGB path: RGBA SharedImage → pass-through → STORAGE|SAMPLED import → VulkanFilterYuvCompute::RGBA2YCBCR on the compute queue → NV12 encode source. Three numbered badges mark the Chromium-side changes.

libyuv (CPU) appears only on CPU-source lanes — it is not part of the §6.3.2 zero-copy path. The one place a GPU-resident frame hits libyuv today is the adapter's non-passthrough branch: a canvas/WebGL RGBA frame fails the pass-through check (video_encode_accelerator_adapter.cc:1085 — requires NV12 or an advertised GPU format, and dev advertises {NV12} only), so the adapter CPU-maps a GMB and runs ConvertAndScale (libyuv, :1123) on pixels that never needed to leave the GPU.

The library already ships the GPU converter VulkanFilterYuvCompute (common/libs/VkCodecUtils/) has an explicit RGBA2YCBCR compute-shader operation (plus YCBCRCOPY, YCBCR2RGBA, subsampling/MSB-shift flags). VkVideoEncoder owns it as m_inputComputeFilter (VkVideoEncoder.h:944, created at VkVideoEncoder.cpp:2118), and the chromium-encode ext API anticipates exactly this: VkVideoEncoderConfig.inputFormat + enablePreprocessFilter ("e.g. RGBA input that needs RGBA→NV12 conversion", vulkan_video_encoder_ext.h:125-128), SupportsFormat(VkFormat) (:453), supportedInputFormats in the G-NEW-1 caps (:540). The compute queue the filter runs on is already enabled on the compositor VkDevice (COMPUTE_QUEUE_FLAG = 0x08) with its family index plumbed via the BYO config (G-NEW-9).

Chromium-side changes: (1) advertise RGBA in VideoEncoderInfo.gpu_supported_pixel_formats (VEA CompleteLibraryInitialize), gated on the library's SupportsFormat(); (2) per-format import usage in ProduceVulkanVideo; (3) route resolved RGBA images through enablePreprocessFilter. Sync shape: acquire semaphores → compute (filter) → encode — one extra queue hop the existing timeline-semaphore/QFOT machinery (DDD §9) already models. The DDD kept CPU-side RGBA readback conversion off-plan deliberately — the compute filter is the mechanism. Related: viz tab-capture in NV12-GMB mode already converts RGBA→NV12 on the GPU (SkiaRenderer CopyOutputRequest blit), so Lane C never involves libyuv either way; the capturer's default is I420 CPU readback (frame_sink_video_capturer_impl.h:153) — keep encode consumers on NV12-GMB mode.

5.2 Zero-copy across window systems — Wayland vs X11 vs the rest

The seam is WS-agnostic; per-WS work is one VulkanImplementation import override plus native-pixmap SharedImage availability.

The seam (usage bit → ProduceVulkanVideo → representation → fallback ladder → counters) is window-system-agnostic. What varies is one hook — VulkanImplementation::CreateImageFromGpuMemoryHandleWithUsage() — plus whether native-pixmap SharedImages exist on the platform:

  • Wayland (Ozone): override present on dev (vulkan_implementation_wayland.cc) — zero-copy works today; P1/P2 tagging needs no new WS work.
  • X11 (Ozone): two independent gaps. (a) No encode-usage override — the base default returns nullptr (vulkan_implementation.cc:86) → staging. Mechanical fix: upstream X11 already has generic dma-buf import (vulkan_implementation_x11.cc:131/:143, DRI3 + DRM modifiers), and the shared vulkan_image_linux.cc machinery (incl. the import-only allocation fix) sits underneath — ~70 lines. (b) The real risk: native-pixmap SharedImages are often unavailable on X11 (esp. NVIDIA) → the adapter's F7 sticky CPU fallback delivers shmem frames → §6.1 staging regardless of any override. Either way encoding still works and is correct — just one CPU copy per frame; that's what --allow-staging distinguishes. Sync detail when porting: X11 imports stamp VK_QUEUE_FAMILY_EXTERNAL where dev's Wayland path uses FOREIGN_EXT — the library's acquire barrier keys off this.
  • ChromeOS / DRM-KMS (Ozone): same OzoneImageBacking/minigbm layer as Wayland; one mechanical override in vulkan_implementation_gbm.cc away — and the platform where NV12 GMB camera frames actually exist, making camera→encoder zero-copy reachable.
  • Windows / Android: dev pre-plumbed the usage bit (d3d_image_backing_factory.cc:256, ahardwarebuffer_image_backing_factory.cc:300); actual representations are future work (DXGI NT-handle / AHB imports per DDD §6.2.2/§6.2.3) — and D3D12/NDK VEAs already serve those platforms, so priority is low.
  • Ozone headless: software-only, no native buffers — can never zero-copy; CI must use headless Weston (C9).

6. Prototyping & testing the use-case graphs

The TEST_PLAN's five tiers validate the codec/VEA surface deeply, but real browser pipeline coverage is its acknowledged gap (MediaRecorder essentially untested end-to-end, Cast absent). The environments below close that gap and are ordered as an escalation ladder — each level proves something the previous one structurally cannot.

L1 unit → L2 Tier-2 gtest (PSNR gate) → L3 browser zero-copy gate → L4 per-use-case suites. The flag bar at the bottom is the exact browser invocation.

6.1 The browser invocation (three features, not one)

chrome --enable-features=AcceleratedVideoEncoder,Vulkan,VulkanVideoEncode \
       --ozone-platform=wayland \
       --enable-logging=stderr --vmodule='*vulkan_video_encode_accelerator*=1' \
       [--ignore-gpu-blocklist] \
       --use-fake-device-for-media-stream --use-fake-ui-for-media-stream \
       --use-file-for-fake-video-capture=/path/1080p.y4m
  • AcceleratedVideoEncoder — the Linux renderer gate (content/renderer/render_thread_impl.cc:991, verified unpatched on dev): without it no renderer ever asks the GPU process for an encoder, regardless of the factory.
  • Vulkan — Skia-on-Vulkan compositing; creates the VulkanDeviceQueue that is the VEA's BYO device (production fail-fasts without it).
  • VulkanVideoEncode — selects the backend in the factory (tried first).
  • The renderer also requires GPU_FEATURE_TYPE_ACCELERATED_VIDEO_ENCODE enabled in GpuFeatureInfo — hence the optional --ignore-gpu-blocklist.

6.2 U3 WebCodecs — available now (P0 regression harness)

  • Page: W3C encode-decode-worker sample (knobs: codec, HW preference, latencyMode, bitrate mode, scalabilityMode L1T1–L1T3; measures per-frame encode delay via frame.timestamp correlation). Pin latencyMode when benchmarking — realtime may drop frames.
  • Gate: media/gpu/vulkan/test/wayland_zero_copy_check.sh — PASS iff zero-copy>0 && staging==0 in the last input-path summary line.
  • Below the browser: Tier-2 video_encode_accelerator_tests --implementation=vulkan incl. Vulkan_EncodePsnr_H264Baseline (--vulkan_psnr_floor, default 38 dB; 51.07 dB measured).

6.3 U1 WebRTC loopback — target of P1

  • Pages: pc1 (minimal loopback; pc1/pc2 page globals → drive getStats() from automation), change-codecs (setCodecPreferences for H.264/AV1), extensions/svc (scalabilityMode — meaningful once G-NEW-6 lands). No simulcast sample exists upstream — use fippo's simulcast-playground.
  • Assert via getStats: encoderImplementation === "VulkanVideoEncodeAccelerator"; framesEncoded advances; totalEncodeTime/framesEncoded < ~33 ms at 30 fps; qualityLimitationReason stays none/bandwidth — never cpu (the top-line "HW is really carrying the load" signal); bitrate (ΔbytesSent×8/Δt) tracks setParameters ramps — expected-fail until G-NEW-3.
  • QP caveat: qpSum/framesEncoded is codec-scale-specific (H.264 0–51 vs VP8 0–127) — never compare across codecs.
  • Story sets: tools/perf/page_sets/webrtc_cases/ (codec_constraints, multiple-peerconnections, pause-play, canvas-capture); ChromeOS tast (video.EncodeAccel.*, webrtc/rtc_peer_connection_perf.go) is the model for real-hardware CI.

6.4 U4 MediaRecorder — cheap E2E win (closes a TEST_PLAN gap)

  • MediaRecorder(stream, {mimeType:'video/mp4; codecs=avc1'}) over a fake-camera stream; exercises VBR + Flush() drain semantics that WebCodecs CQ mode does not.
  • Assert HW selection (chrome://media-internals), zero-copy counters, and that the produced file demuxes and decodes (ffprobe/ffmpeg) with sane PSNR vs the .y4m source.

6.5 U2 screen share / U5 cast — target of P2 (strict)

  • getDisplayMedia({video:true}) + --auto-select-tab-capture-source-by-title=… feeding a loopback PC. The upstream getdisplaymedia sample only captures — combine with capture/video-pc/ or hand-roll the PC.
  • U5: Cast is HW-first by default (CastStreamingOfferHardwareFirst); pin the codec with --cast-streaming-force-enable-hardware-h264; sink = openscreen cast_receiver demo or a second Chrome.
  • Acceptance is strict staging==0 — this graph has no legitimate CPU hop; any staging tick means a lost tag or a modifier-incompatible pool buffer.
  • Perf probe: SW-control run (--disable-features=VulkanVideoEncode) vs Vulkan run at 1080p30/4K30: GPU-process CPU% (pidstat) + nvidia-smi --query-gpu=utilization.encoder,encoder.stats.sessionCount,encoder.stats.averageFps,encoder.stats.averageLatency (or nvidia-smi encodersessions; note utilization.encoder is busy-time %, not throughput).

6.6 CI shape

  • Each browser job = launch script + page + stderr grep + getStats JSON dump, on a headless-Weston session on the NVIDIA runner (Chromium's own Wayland bots use testing/xvfb.py --use-weston with --ozone-platform=wayland). Promote to the TEST_PLAN Tier-4 lane; keep Tier-2 gtests as the per-CL gate; browser jobs nightly.
  • The Ozone headless platform is software-only — it cannot host these jobs. Headless-mode Chrome with --enable-gpu needs a real display server; the --use-angle=vulkan workaround covers WebGL only, not our path.
  • Ubuntu 24.04 AppArmor user-namespace restrictions break unpackaged builds; apply the documented AppArmor profile fix rather than --no-sandbox (sandbox-off runs don't exercise production GPU-process brokering).

7. Caveats — verified traps, each one cost someone a debugging day

C1 · The browser-run flag set is three features, not one The renderer-side gate at content/renderer/render_thread_impl.cc:991 means VulkanVideoEncode alone gets the backend registered but no renderer will ever ask for it — WebRTC/WebCodecs/MediaRecorder all silently use software. You need AcceleratedVideoEncoder (renderer gate) + Vulkan (BYO compositor VkDevice) + VulkanVideoEncode (backend selection). Verified unpatched on dev.
C2 · Feature renamed at M131; no flags UI on Linux VaapiVideoEncoder → AcceleratedVideoEncoder at M131 — the old spelling silently does nothing. chrome://flags has no entry for it on Linux (about_flags.cc scopes disable-accelerated-video-encode to Mac/Win/CrOS/Android); the command line is the only way.
C3 · --enable-features=Vulkan ≠ --use-angle=vulkan The former is Skia-on-Vulkan compositing (what we need — it creates the compositor VulkanDeviceQueue); the latter is ANGLE's WebGL backend and does nothing for encode. Colab/WebGPU recipes that pass --use-angle=vulkan are not applicable here.
C4 · gtests structurally cannot prove zero-copy A unit-test process has no GPU-service SharedImages and no compositor VkDevice — the Tier-2 harness runs on the library's own device via the test-only SetAllowLibraryDeviceForTesting(). Only browser-level runs (the counter grep / gate script) prove the seam. Budget CI accordingly.
C5 · WebCodecs cannot tell you which encoder it used Unlike WebRTC's encoderImplementation stat, WebCodecs has no implementation-report API (w3c/webcodecs#604); isConfigSupported is a hint the UA may ignore (anti-fingerprinting). Ground truth: chrome://gpu Encode rows, chrome://media-internals, vmodule logs.
C6 · webrtc-internals impl fields need active capture encoderImplementation / powerEfficientEncoder "MUST NOT exist unless exposing hardware is allowed" — the page must have a live getUserMedia/getDisplayMedia capture. Receive-only pages never show them. Pre-info fallback value is "ExternalEncoder".
C7 · Import-only vkAllocateMemory for dma-buf imports Chaining VkExportMemoryAllocateInfo on an import made the NVIDIA driver return a fresh zeroed allocation — every zero-copy frame encoded solid black with no validation error (fixed on dev in gpu/vulkan/vulkan_image_linux.cc). If frames go black on a new platform, audit the allocation pNext chain first.
C8 · LINEAR-modifier multiplanar imports can't be encode sources (A4000/615.06) The Wayland VulkanImplementation strips VIDEO_ENCODE_SRC for DRM-modifier-0 NV12 imports (no encode format feature) — those frames take the library's GPU staging copy (still zero CPU). Expect staging ticks from LINEAR pool buffers, not a bug in the seam.
C9 · Ozone "headless" is software-only; sandbox-off hides bugs Use headless Weston (the upstream bot pattern) for CI, not --ozone-platform=headless. Prefer the Ubuntu 24.04 AppArmor profile fix over --no-sandbox — the sandbox affects GPU-process brokering that this feature exercises.
C10 · Metric semantics qpSum scales are codec-specific (H.264 0–51, VP8 0–127) — never cross-codec-compare. nvidia-smi utilization.encoder is busy-time percent, not throughput. WebRTC adaptation shows a healthy HW encoder as qualityLimitationReason ∈ {none, bandwidth}; cpu means fallback or overload.
C11 · RequestEncodingParametersChange is a no-op today Both overloads are documented no-ops pending library G-NEW-3 (Reconfigure) and G-NEW-6 (temporal layers). WebRTC's congestion controller cannot steer bitrate — fine for demos, wrong for shipping; encode U1 bitrate-tracking assertions as expected-fail until the library lands them.
C12 · VA-API-on-NVIDIA is off anyway kVaapiOnNvidiaGPUs is default-disabled (crbug.com/1492880) — don't burn time comparing against a VA-API baseline on the NVIDIA runner; the meaningful control run is software (--disable-features=VulkanVideoEncode).
C13 · GPU RGBA frames silently drop to CPU libyuv in the adapter Pass-through (adapter.cc:1085) requires the frame format to be NV12 or listed in VideoEncoderInfo.gpu_supported_pixel_formats (dev: {NV12} only) — a GPU-resident canvas/WebGL RGBA frame gets CPU-mapped and converted by ConvertAndScale (:1123). Fix = P3-RGBA (§5.1): advertise RGBA formats and let the library's VulkanFilterYuvCompute::RGBA2YCBCR compute filter convert on-GPU. Watch for it in profiles as unexpected ConvertAndScale samples under encode.
C14 · Zero-copy is Wayland-only today; X11 silently degrades to staging Only VulkanImplementationWayland overrides the encode-usage import; on X11 (and DRM/GBM) the base default returns nullptr and every frame takes the staging ladder — correct output, one extra CPU copy, easy to miss because nothing errors. The staging counter is the tell. X11 additionally risks the F7 CPU-frame fallback when native-pixmap SharedImages are unavailable (common on NVIDIA X11). Run zero-copy work and gates on --ozone-platform=wayland.
