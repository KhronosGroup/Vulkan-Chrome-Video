1. Executive Summary

1.1 Project Goal

Integrate Vulkan Video decode and encode extensions as a first-class hardware acceleration backend in Chromium, alongside existing VA-API support, to provide:

  • Cross-platform hardware video acceleration
  • Vendor-agnostic implementation
  • Modern GPU integration with the Vulkan graphics pipeline
  • Future-proof architecture for emerging codecs

🔑 Key Insight: Codec Parsers are Shared

Critical discovery: Chromium's architecture separates:

  • Codec Parsing (shared) - in media/parsers/ and media/gpu/*_decoder.{h,cc}
  • Hardware Acceleration (per-backend) - in media/gpu/vaapi/, media/gpu/v4l2/

This means Vulkan Video integration does NOT require reimplementing codec parsing. However, significant conversion work is still required.

What we DON'T need to do:
  • Write bitstream parsers (NAL unit parsing, entropy decoding)
  • Implement DPB management logic
  • Handle reference frame tracking
What we DO need to do:
  • Implement the *Accelerator interface for each codec
  • Write conversion code from Chromium's parsed structures to Vulkan Video's StdVideo* structures
  • This conversion is non-trivial: ~500-700 lines per codec
⚠️ Important Note on NVPRO Sample

The official NVIDIA Vulkan Video sample (NVPRO) includes its own integrated parser. We cannot reuse this parser because Chromium's *Accelerator interface receives already-parsed Chromium structures, not raw bitstream. We must write the conversion layer:

Codec Chromium Structures Vulkan Structures Est. Code
H.264H264SPS, H264PPS, H264SliceHeaderStdVideoH264*~500 lines
H.265H265VPS, H265SPS, H265PPSStdVideoH265*~700 lines
VP9Vp9FrameHeader, Vp9SegmentationParamsStdVideoDecodeVP9*~400 lines
AV1libgav1::ObuSequenceHeaderStdVideoAV1*~600 lines

Total estimated conversion code: ~2,200 lines across 4 codecs.

3.3 H264Accelerator Interface

This is the interface that hardware backends implement:

// media/gpu/h264_decoder.h - The Accelerator interface

class H264Accelerator {
 public:
  // Create a picture buffer for decoded output
  virtual scoped_refptr<H264Picture> CreateH264Picture() = 0;
  
  // Submit SPS/PPS for HW configuration
  virtual void ProcessSPS(const H264SPS* sps, base::span<const uint8_t> data);
  virtual void ProcessPPS(const H264PPS* pps, base::span<const uint8_t> data);
  
  // Submit frame decode parameters
  virtual Status SubmitFrameMetadata(
      const H264SPS* sps,
      const H264PPS* pps,
      const H264DPB& dpb,                    // Reference frames
      const H264Picture::Vector& ref_list_p0,
      const H264Picture::Vector& ref_list_b0,
      const H264Picture::Vector& ref_list_b1,
      scoped_refptr<H264Picture> pic) = 0;
  
  // Submit slice data
  virtual Status SubmitSlice(...) = 0;
  
  // Execute decode operation
  virtual Status SubmitDecode(scoped_refptr<H264Picture> pic) = 0;
};

6. Protected Content (DRM) Architecture

📊 DRM Architecture

Open diagram in new tab ↗

6.1 Protected Content Components

Protected content flows through multiple security boundaries:

  1. EME API (JavaScript) - Web application requests media key access
  2. CDM Host - Browser manages Content Decryption Module interface
  3. Widevine CDM - License negotiation, key management
  4. VaapiVideoDecoderDelegate - Sets up protected VA-API session
  5. Hardware TEE - Secure key unwrap and decode
  6. HDCP - Protected output to display

6.2 ChromeOS Protected Session Flow

SetupDecryptDecode(...) {

  }
  
  return ProtectedSessionState::kCreated;
}

✓ Vulkan Video Protected Content - Simpler than VA-API!

Vulkan uses a cleaner architecture than VA-API's decrypt-during-decode:

  1. CDM decrypts slices into a protected VkBuffer
  2. Decoder reads from protected buffer (decrypted bitstream)
  3. Decoder writes to protected VkImage
  4. Security boundary is the protected memory, not the decode operation

Key insight: The decoder doesn't need crypto awareness - it just decodes! The CDM handles all decryption, writing clear NAL units to protected memory that unprivileged code can't read.

6.5 Vulkan Protected Content API

// CDM allocates protected buffer for decrypted bitstream
VkBufferCreateInfo buffer_info = {...};
vkCreateBuffer(device, &buffer_info, nullptr, &protected_bitstream);

VkMemoryAllocateInfo alloc = {
    .memoryTypeIndex = FindMemoryType(VK_MEMORY_PROPERTY_PROTECTED_BIT),
};
vkAllocateMemory(device, &alloc, nullptr, &protected_memory);
vkBindBufferMemory(device, protected_bitstream, protected_memory, 0);

// CDM writes decrypted NAL units to protected_bitstream

// Decoder just decodes - NO crypto parameters needed!
VkVideoDecodeInfoKHR decode_info = {
    .srcBuffer = protected_bitstream,       // Decrypted slices
    .srcBufferOffset = slice_offset,
    .srcBufferRange = slice_size,
    .dstPictureResource = protected_output, // Protected VkImage
};
vkCmdDecodeVideoKHR(protected_cmd_buffer, &decode_info);

🔑 Why This is Simpler than VA-API

VA-API: Driver must handle VAEncryptionParameters, decrypt-during-decode, key injection

Vulkan: CDM decrypts → protected buffer → decoder just decodes. No special integration needed!

6.6 Recommendation: Native Decrypt-During-Decode Extension

📊 Future: Vulkan Video with Native Decryption Support

Open diagram in new tab ↗

💡 Future Enhancement for Vulkan Video

While the protected buffer approach works, it would be desirable for Vulkan Video to add native support for decryption keys, similar to VA-API's VAEncryptionParameters:

// Hypothetical future Vulkan Video extension: VK_KHR_video_decode_encryption
VkVideoDecodeEncryptionInfoKHR encryption_info = {
    .sType = VK_STRUCTURE_TYPE_VIDEO_DECODE_ENCRYPTION_INFO_KHR,
    .encryptionScheme = VK_VIDEO_ENCRYPTION_SCHEME_CENC_CTR_KHR,
    .pKeyData = wrapped_key_blob,
    .keyDataSize = 16,
    .pIV = initialization_vector,
    .pSubsampleInfo = subsample_entries,
};

VkVideoDecodeInfoKHR decode_info = {
    .pNext = &encryption_info,  // Attach encryption params
    .srcBuffer = encrypted_bitstream,
    .dstPictureResource = protected_output,
};

Benefits of native decrypt-during-decode:

  • Single HW operation: Decrypt and decode in one pass
  • Keys never leave TEE: Hardware-wrapped keys go directly to secure enclave
  • Reduced memory bandwidth: No separate decrypt step
  • Parity with VA-API: Easier porting of existing DRM implementations
  • Simpler CDM integration: CDM only provides keys, doesn't handle decryption

7. Synchronization Mechanisms

📊 Synchronization Timeline

Open diagram in new tab ↗

7.1 VA-API Synchronization

// Implicit sync (most common on Intel)
vaEndPicture(display, context);  // Implicitly syncs

// Explicit sync (required for multi-threaded scenarios)
vaSyncSurface(display, surface_id);  // Blocks until decode completes

7.2 Vulkan Video Synchronization

// Explicit fence-based sync
VkFence decode_fence;
vkCreateFence(device, &fence_info, nullptr, &decode_fence);

VkSubmitInfo submit = {
    .commandBufferCount = 1,
    .pCommandBuffers = &cmd_buffer,
};
vkQueueSubmit(decode_queue, 1, &submit, decode_fence);

// Wait for decode completion
vkWaitForFences(device, 1, &decode_fence, VK_TRUE, UINT64_MAX);

// Semaphore-based sync (for queue transitions)
VkSemaphore decode_complete;
VkSubmitInfo decode_submit = {
    .signalSemaphoreCount = 1,
    .pSignalSemaphores = &decode_complete,
};
