2. Sufficiency assessment per Chromium requirement

26 requirements from v1.1: 11 covered, 3 partial, 12 gaps (4 of which are critical P0 ship blockers).

The headline: 11 / 26 covered, 3 / 26 partial, 12 / 26 gaps. Most gaps are interface-shape, not implementation-shape — the underlying EncoderConfig struct already carries most of what's missing from the public VkVideoEncoderConfig.

2.1 Per-gap deep-dive

Each missing or partial feature, broken down: (a) what Chromium calls for — the caller, the API it expects, and when, (b) what underlying APIs are involved at the Vulkan, Std-Video, and Chromium VEA layers, (c) what the library does today, (d) why it's missing, and (e) the concrete proposed delta.

A handful of gaps had more than one reasonable closure shape. The chosen alternative is named in the section heading (e.g. "WebRTC index model", "BYO primary + ephemeral fallback") and justified in the deep-dive itself. The ambiguous design points were temporal SVC depth, manual-reference-buffer API shape, output-buffer ownership, capability-enumeration entry point, resize-IDR semantics, and trusted-rate-controller surfacing.

Notation: G-NEW-N. Throughout this document the label G-NEW-N (read: Gap-resolving New extension #N) refers to a specific additive contribution to the Vulkan-Video-Samples public API that closes one or more gaps from the sufficiency table. The eleven proposed extensions (G-NEW-1 … G-NEW-11) are catalogued in §3 with full specifications and LoC estimates. Each is a non-breaking additive change to the public header (vulkan_video_encoder_ext.h) — existing cmdline callers continue to compile and run unchanged.
Driver capability assumption. For every gap below that maps onto a Vulkan extension or optional capability, the answer to "does my GPU support it?" is query the driver at runtime. The Chromium-side wrapper consults vkGetPhysicalDeviceVideoCapabilitiesKHR, vkGetPhysicalDeviceVideoFormatPropertiesKHR, and the relevant VkPhysicalDeviceVideoEncode*FeaturesKHR chain at session-creation time and exposes downstream features (WebCodecs options, VideoEncoderInfo fields, SDP capability) only when the driver reports support. We do not bake any vendor matrix into Chromium code; this document deliberately avoids per-vendor capability claims.

Gap #10 — Quantization map (VK_KHR_video_encode_quantization_map)

What Chromium calls for. A per-block delta-QP image that nudges the encoder toward higher or lower quality regions per frame. Two scenarios:

  1. WebCodecs scalar quantizer. VideoEncoder.encode(frame, { quantizer: 28 }) — integer per encode call.
  2. ROI / screen-share delta-QP. Tab-capture / screen-share computes a delta-QP map per frame (lower QP on text regions, higher on static areas).

Underlying APIs.

  • Vulkan extension VK_KHR_video_encode_quantization_map. Adds VkVideoEncodeQuantizationMapInfoKHR in pNext of VkVideoEncodeInfoKHR; driver caps via VkPhysicalDeviceVideoEncodeQuantizationMapFeaturesKHR::videoEncodeQuantizationMap + per-codec quantizationMapTexelSize.
  • Two modes: delta-QP map (VK_VIDEO_ENCODE_WITH_QUANTIZATION_DELTA_MAP_BIT_KHR) and emphasis map (VK_VIDEO_ENCODE_WITH_EMPHASIS_MAP_BIT_KHR).
  • Chromium: media::VideoEncoder::EncodeOptions::quantizer scalar today; ROI plumbing would add a quantization_map field.

Library internals (verified citations). The library has the full machinery wired; only the public surface is missing.

Gap #11 — Intra-refresh (VK_KHR_video_encode_intra_refresh)

What Chromium calls for. WebRTC packet-loss recovery uses progressive intra-refresh: instead of issuing an IDR (a several-kilobyte bitrate spike), the encoder refreshes a strip of macroblocks per frame, completing a full cycle over N frames. The result is identical to an IDR for keyframe purposes but with a near-flat bitrate profile. WebRTC also wants per-frame control: don't refresh during congestion windows, force a refresh after a NACK storm.

Underlying APIs.

  • Vulkan extension VK_KHR_video_encode_intra_refresh:
    • VkVideoEncodeIntraRefreshInfoKHR chained per-frame; carries intraRefreshIndex.
    • VkVideoEncodeSessionIntraRefreshCreateInfoKHR chained at session creation; carries intraRefreshMode + intraRefreshCycleDuration.
  • intraRefreshMode enum: PER_PICTURE_PARTITION (slice/tile), BLOCK_BASED (horizontal strip — most common), BLOCK_ROW_BASED, BLOCK_COLUMN_BASED.
  • Driver caps: VkPhysicalDeviceVideoEncodeIntraRefreshFeaturesKHR::videoEncodeIntraRefresh, VkVideoEncodeIntraRefreshCapabilitiesKHR::supportedIntraRefreshModes / maxIntraRefreshCycleDuration / maxIntraRefreshActiveReferencePictures.
  • Chromium API: today not directly exposed at VEA layer; WebRTC's H264EncoderImpl ships SW-side intra-refresh. With Vulkan we have HW support; plumb new VEA::Config::intra_refresh_period (cycle length, set at Initialize) and per-frame EncodeOptions::intra_refresh_strip (override).

Library internals.

// VkVideoEncoder.cpp:2605-2614

Why missing. Sample-app design — set once at startup. Per-frame override is the live-API use case.

Proposed delta (G-NEW-5).

VkBool32  intraRefreshStartCycle; // resets the cycle counter (used after NACK)

Validation approach. Encode 60 frames at 30 fps, cycle duration = 30, observe per-frame bitstream sizes: same global QP, an IDR is ~10× a P-frame; intra-refresh frames should be ~1.5–2× P-frame. Decode + psnr_per_frame; quality should be flat across the cycle, not spike at the IDR boundary.

Gap #12 — Temporal SVC (T=2/3/4) — deep scope

What Chromium calls for. WebRTC simulcast and SVC adaptive streaming. VideoBitrateAllocation is a 2D matrix bitrates[spatial][temporal] up to kMaxSpatialLayers=5 × kMaxTemporalStreams=4 = 20 entries. Each temporal layer encodes only frames at specific positions in a 2-/4-/8-frame pattern; layer 0 is the base layer. A client can drop layers under congestion and continue decoding the base.

Underlying APIs.

  • Vulkan: per-layer rate control via the pLayers array in VkVideoEncodeRateControlInfoKHR::pLayers[VkVideoEncodeRateControlLayerInfoKHR].
  • Std-Video: per-frame StdVideoEncodeH264SliceHeader::temporal_id, StdVideoEncodeH265SliceSegmentHeader::nuh_temporal_id_plus1, StdVideoEncodeAV1PictureInfo::temporal_id.
  • GOP: each frame's temporal-layer membership is fixed by the GOP pattern (e.g., T=3 pattern [T0 T2 T1 T2 T0 T2 T1 T2]).
  • Chromium API: media::VideoBitrateAllocation (2D), VideoEncodeAcceleratorConfig::spatial_layers[].num_of_temporal_layers, H264Metadata::temporal_idx / Vp9Metadata::temporal_idx / SVCGenericMetadata::temporal_idx.

Library internals.

Gap #13 — Spatial SVC (S=2 / S=3)

What Chromium calls for. WebRTC VP9 SVC + AV1 SVC: encode the same scene at multiple resolutions in one bitstream. Used in conferencing for variable network conditions.

Underlying APIs.

  • Vulkan: no dedicated extension. Spatial SVC has to be implemented as multiple parallel VkVideoSessionKHR instances, each at a different resolution, with reference-picture sharing between them. Khronos has discussed a future extension; as of mid-2026 nothing exists.
  • AV1 spec: native support via obu_extension_header_flag + spatial_id. Vulkan AV1 encoding doesn't expose this.
  • H.264 SVC: dropped from the spec long ago.
  • HEVC: SHVC (scalable HEVC) extension exists but is essentially never implemented in HW encoders.

Today. Not implemented in the library.

Why missing. No spec extension to implement against. Even if there were, no current HW encoder hardware supports spatial SVC natively — it would have to be simulated via multiple parallel sessions, which has tricky reference-frame consistency requirements.

Proposed delta. Deferred to P3 (post-MVP). Document the workaround: multiple independent VEAs, one per resolution — that's how Chrome ships HW-accelerated simulcast today via VA-API and D3D12. Native single-bitstream SVC waits for a Khronos spec. Estimated ~1,500 LoC (when/if the spec exists).

Gap #14 — Manual reference buffer control — WebRTC index model

What Chromium calls for. WebRTC VideoEncodeAcceleratorConfig::manual_reference_buffer_control = true flips the encoder from "GOP-driven reference management" to "caller tells you which reference to use". Three use cases:

  1. Packet-loss-resilience. After a NACK, the encoder is told "don't reference frame N (lost) — reference frame N-2 instead".
  2. Screen content. Only encode I-frame + delta from a stable "long-term reference"; never reference recent frames.
  3. Simulcast layer prediction control. Each spatial layer references only frames within its own layer.

WebRTC models this as a small fixed-size buffer pool (typically 8 slots, "frame buffers" in VP8/VP9 terminology). Per frame, caller passes frame_buffer_indices describing which slots are refs and which to update.

Underlying APIs.

  • Vulkan: VkVideoEncodeInfoKHR::pSetupReferenceSlot (the slot the encoder writes to) + VkVideoEncodeInfoKHR::pReferenceSlots[] (the refs).
  • Std-Video: codec-specific reference lists (RefPicList0 / RefPicList1 for H.264; ref_frame_idx[7] for AV1).
  • Chromium API: VideoEncodeAccelerator::Config::manual_reference_buffer_control flag; per-frame metadata SVCGenericMetadata::reference_flags (16-bit bitmask of which 8 buffers are refs) and refresh_flags (which to update).

Library internals. VkEncoderDpb{H264,H265,AV1} manages reference slots internally based on the GOP structure. Internal stdReferenceSlotInfo[] array; no public override.

Why missing. Cmdline sample uses a fixed IPPP / IBP / IPBBB pattern; the GOP machinery is sufficient. Exposing a per-frame override means library has to (a) trust the caller, (b) validate the slot configuration against codec rules, (c) update its own DPB tracking. Surgery on the DPB layer.

Proposed delta (WebRTC index model; G-NEW-7).

Library implementation: bypasses VkEncoderDpb*::Update(), instead uses the caller's pFrameBufferIndices as the slot-occupancy oracle. Translates the index model to VkVideoReferenceSlotInfoKHR[]; validates against codec rules (H.264 num_ref_frames, HEVC sps_max_dec_pic_buffering_minus1, AV1 ref_frame_idx[7] ordering).

Alternative slot-based API not chosen. The Vulkan-native shape (VkVideoReferenceSlotInfoKHR[] + pSetupReferenceSlot) is more flexible but verbose and harder to maintain DPB consistency. The WebRTC index model maps cleanly to all three codecs and matches what Chromium VEA already speaks at the SVCGenericMetadata::reference_flags level.

Validation approach. Run a "NACK simulation" test: encode 100 frames with the GOP-driven path, drop frame 50 from the decoder, encode 100 more with manual ref control where frame 51 references frame 49 instead of 50; verify the resulting bitstream decodes without errors and PSNR doesn't drop more than 1 dB at the recovery point.

Gap #15 — Per-frame QP map binding

Relationship to #10. #10 is "expose the feature at all"; #15 is "expose it on a per-frame basis (not just at session creation)". The library's design conflates the two: EncoderConfig::enableQpMap is a session-wide flag, and the per-frame QP map is fetched from disk via EncoderQpMapFileHandler::GetQpMapForFrame(encodeOrderIndex). There is no API surface for "this frame has a different QP map".

What Chromium calls for. Per-frame quantizer / QP-delta map provided by the caller at encode time:

  • WebCodecs EncodeOptions::quantizer (scalar): WebCodecs delivers this with the encode() call. Each frame can carry a different value.
  • ROI / screen-share delta map: each frame has a fresh map based on tab-capture analysis. The map can change at every frame (e.g., a text cursor moving picks up high-priority blocks).

Library internals. Mechanism is per-frame; just the delivery of the QP map is file-only.

Gap #18 — Format negotiation (SupportsFormat, max-size queries)

What Chromium calls for. Three downstream surfaces consume this data:

  1. gpu::GPUInfo::video_encode_accelerator_supported_profiles — populated at GPU-process startup; available in chrome://gpu and via gpu::GpuInfo Mojo.
  2. WebRTC SDP capability — RTCRtpSender::getCapabilities('video') returns the codecs the browser advertises.
  3. WebCodecs VideoEncoder.isConfigSupported(config) — short-circuits if format/codec/resolution isn't supported.

For all three, the per-profile data needs to be driver-accurate, not a hardcoded list. Hardcoding "8192×8192 max" on a 4K-only adapter means VideoEncoder.isConfigSupported({ width: 7680 }) returns true and then encode() fails — poor DX.

Underlying APIs.

  • Vulkan: vkGetPhysicalDeviceVideoFormatPropertiesKHR returns VkVideoFormatPropertiesKHR[] with format, componentMapping, imageType, imageTiling, imageUsageFlags, maxExtent.
  • Vulkan: vkGetPhysicalDeviceVideoCapabilitiesKHR returns VkVideoCapabilitiesKHR::minCodedExtent / maxCodedExtent / pictureAccessGranularityWidth/Height / maxDpbSlots / maxActiveReferencePictures, plus chained VkVideoEncodeCapabilitiesKHR::maxBitrate / maxQualityLevels / rateControlModes, plus codec-specific chained structs.

Today in the library.

Zero-copy across the process boundary

Pixel data does not traverse the Mojo pipe. The encode flow uses the existing EncodeCommandBufferId back-channel:

// media/mojo/mojom/video_encode_accelerator.mojom:62-65
struct EncodeCommandBufferId {
  mojo_base.mojom.UnguessableToken channel_token;
  int32 route_id;
};
  1. Renderer's VideoFrame is backed by a SharedImage mailbox (canvas / tab capture / camera).
  2. Renderer's MojoVideoEncodeAccelerator sends Encode(frame, options) with the mailbox token + EncodeCommandBufferId{channel_token, route_id}. No pixel bytes in the Mojo payload.
  3. Utility process uses EncodeCommandBufferId to ask the GPU process's CommandBufferStub for the actual backing.
  4. GPU process exports a DMA-BUF FD (Linux) / shared NT handle (Windows) / AHardwareBuffer (Android). The kernel duplicates the FD into the utility process's FD table. The pixel pages live in DRAM exactly once.
  5. Utility process imports the FD into its own VkDevice via VkImportMemoryFdInfoKHR + VkImageDrmFormatModifierExplicitCreateInfoEXT. The library's Path A consumes the imported VkImage directly.
  6. vkCmdEncodeVideoKHR runs in the utility process. Bitstream goes into VkVideoEncodeResult::pBitstreamData.
  7. Bitstream flows back over Mojo as mojo_base.mojom.UnsafeSharedMemoryRegion (pre-shared via UseOutputBitstreamBuffer()). It's small (~kilobytes/frame), so the Mojo cost is negligible.
